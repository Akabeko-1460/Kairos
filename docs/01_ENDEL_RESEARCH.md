## 1. Endel とは何か

Endel は「音楽アプリ」ではなく **機能性サウンドスケープ（functional soundscape）** のアプリです。
公式は「Endel は楽しませるためではなく、回復させるために設計されている。芸術的表明ではなく、
精神状態を良くするための、終わりなく適応し続ける背景音である」という趣旨を明言しています。
ここが Spotify のプレイリストや通常のBGMアプリとの決定的な違いです。

対応プラットフォームは iOS / Android / macOS / Windows / Apple Watch / Apple TV / Apple Vision Pro / Alexa / Web と非常に広く、
Apple Watch アプリは 2020 年の Apple Watch App of the Year を受賞しています。

## 2. コンテンツの2分類（本プロジェクトに直結する最重要ポイント）

Endel の音は公式に **2種類**に分けられています。

### Soundscapes（サウンドスケープ）
- **端末上で無限に生成され続ける**音
- ローカルな入力（天候・時刻・歩行のケイデンス・心拍など）に追従して変化する
- 代表: Focus / Relax / Sleep / Move / Study / Colored Noise など

### Scenarios（シナリオ）
- **あらかじめロジックが定義された、時間制限付きのセッション**
- 設定したタイマー長に対して「**開始 / 中間 / 終了**」の各フェーズが定義され、事前生成される
- 特定のタスクや場面のために設計されている
- 代表: Focus Timer, Deep Work, Quick Task, Power Nap, Meditate, Read, Create, Binaural Beats など

> **本プロジェクトが真似るべきは Scenarios の設計思想です。**
> 「25分」という有限の時間枠に対して、始まり・中盤・終わりの3フェーズを持つ音の弧を描く。
> これが単なる「ループBGMの垂れ流し」との違いを生みます。

### Focus Timer（＝本プロジェクトの直接の参照元）
Endel には **Focus Timer** というシナリオがあり、公式サイトで
「**ポモドーロ・テクニックに基づく**」機能だと明記されています。
- 作業を扱いやすいインターバルに分割する
- **Task Headline**（そのセッションで取り組むタスク名）を書いて表示し続ける
- 作業／休憩のインターバル長をユーザーが設定する
- ユーザーレビューでは「事前にラウンド数をまとめて設定できること」が重要という声がある
  （毎回タイマーを再設定させられるのは集中の妨げになる、という指摘）

→ **示唆:** 「タスク名の表示」と「ラウンド数の事前設定＋自動継続」は MVP に入れるべき機能です。

## 3. 技術構造（Endel Pacific）

公式の technology ページによれば、特許取得済みの生成エンジン「Endel Pacific」は4層構造です。

| 層 | 内容 |
|---|---|
| **Inputs** | 就寝時刻、自然光レベル、天候、時刻からサーカディアンリズムを推定。加えて心拍（Apple Watch）、頭部位置（空間オーディオ）、モーションデータなどのリアクティブな入力 |
| **Core AI Logic** | 入力からリスナーのプロファイルを作り、それをサウンドスケープのロジックへ「AI駆動のノードシステム」でマッピング |
| **Sound generation** | **音のロジックと音素材はサウンドチームが事前にデザインし、各サウンドスケープに割り当てられている。** コアロジックに駆動され、入力が変わるとその場で音が適応する |
| **Output** | 各デバイス |

> **最重要の発見:**
> Endel は「AIがゼロから作曲している」わけではありません。
> **人間が作った音素材＋ルールベース／確率的な組み立てロジック**が実体です。
> したがって本プロジェクトも「実行時にAIモデルを走らせる」必要はなく、
> **AIで作った素材を、賢い組み立てロジックで無限に鳴らす**方式が正解になります（`04_SOUND_ENGINE.md`）。

その他の技術的事実:
- チューニングは **440Hz**。音程間の関係が脳にとって処理しやすく、音楽情報の知覚における認知負荷を下げるという理由
- バイノーラルビートは **専用シナリオのみ**で使用。他の音では使っていない
- 生成は基本的に**オンデバイス**（＝オフラインでも鳴る）
- Mercedes-Benz、Sony（LinkBuds）、Amazon Music などへの外部組み込み実績あり

## 4. 音のデザイン原則（science ページより）

### Focus（集中）
- **一定のビート**が長時間の集中を助けるという研究を根拠に、生産性向上系サウンドスケープ全ての基礎に据えている
- 「**刺激的だが、決して気を散らさない**」——通常の音楽は注意を奪うが、Endel は注意を引かずに集中を促す配置にしている
- サーカディアンリズムの高低に応じて**強度（intensity）を変える**。低調期には集中を促しつつも激しくしすぎない
- Csikszentmihalyi のフロー理論を設計の背骨にしている
- 2022年の査読付き研究（Arctop 実施、脳波計測）で、プレイリストや無音と比較して集中の持続性が高いと報告されている

### Relax（リラックス）
- **脳が処理しやすい単純な音構造**を使い、思考を解きほぐし脳疲労とコルチゾールを下げる
- **自然音**（森・雨・波など）を多用。自然音の鎮静効果に関する研究を根拠にしている
- 副交感神経を活性化させることが休息の前提だとしている

### Sleep（参考）
- カラードノイズ（ピンクノイズ等）による**サウンドマスキング**で外部の音を遮る

> **示唆（Focus と Break の作り分け）:**
> | | Focus | Break |
> |---|---|---|
> | 拍 | 一定のパルスあり | パルスなし／極めて緩やか |
> | 構造 | 変化を最小限に、予測可能に | 単純な構造、広がりのある響き |
> | 素材 | 合成音・薄いノイズ層 | 自然音（雨・波・鳥） |
> | 目的 | 注意を引かずに覚醒度を保つ | 副交感神経を優位にする |

## 5. 本プロジェクトが「真似るもの / 真似ないもの」

### 真似る（設計思想として）
- ✅ シナリオ＝**有限時間に対する開始/中間/終了の3フェーズ設計**
- ✅ 素材＋組み立てロジックによる**無限生成**（同じ演奏が2度と起きない）
- ✅ Focus は「一定のパルス＋変化の最小化」、Break は「自然音＋広い残響＋拍なし」
- ✅ 440Hz チューニング、スケール制約による常時協和
- ✅ 極端にミニマルで気を散らさない UI（Endel の Mac 版は「控えめで邪魔をしない UI」を掲げている）
- ✅ Task Headline とラウンド数の事前設定

### 真似ない（スコープ外 or 権利上の理由）
- ❌ Endel の音源・ロゴ・商標・UI意匠そのもの（**厳禁**）
- ❌ サーカディアンリズム推定・心拍連動・気象連動 → Phase 4 以降の任意拡張
- ❌ 「集中力7倍」等の効果訴求 → 自前のエビデンスがないため書かない
- ❌ バイノーラルビート → 効果に議論があり、初期スコープ外
- ❌ ストリーミング配信・スマートスピーカー連携

## 7. 追加調査（rev.2）— Endel は何で作られているか

「Endel と同じ技術を選ぶべきか」を判断するために追加調査した結果です。

### 結論: ネイティブ実装。Flutter でも React Native でもない

**根拠1: Apple 公式が Core Audio / AVFoundation の使用に言及**
Apple Developer の空間オーディオ特集で、Endel はマルチチャンネルミックス、Core Audio、
AVFoundation を使っていると明記されています。この作業を主導したのは共同創業者兼CTOの
Kyrylo Bulatsev で、「どの音をいつ鳴らすかに加えて、音がどこにあってどう動くかまで
考える必要があった」と語っています。
→ Apple プラットフォームは Swift / Objective-C のネイティブ実装。

**根拠2: 対応プラットフォームが決定的**
Endel は standalone の Apple Watch アプリ、Apple TV、Apple Vision Pro を出しています。
**watchOS / tvOS / visionOS は Flutter も React Native もサポートしていません。**

正確な言語構成は公表されていませんが、Apple 側は Swift、Android 側は Kotlin +
ネイティブ音声レイヤー、エンジン本体（Endel Pacific）は複数プラットフォームで共有するために
C++、という構成が最も自然です。

### エンジンの実体（一次情報）

TechCrunch の共同創業者インタビューで、エンジンの中身が具体的に語られています。

> サウンドスケープはステムベースで、アプリは膨大なサンプルとステムのライブラリを持ち、
> アルゴリズムが適切なステムを選んでシーケンスを組み立てる。
> その基本的なシーケンシングの上に、ソフトウェアがさらに調整を重ねる。

**これは `04_SOUND_ENGINE.md` のレイヤー合成アーキテクチャそのものです。**
設計の方向性が一次情報で裏付けられました。

### 本プロジェクトへの示唆

- **フレームワークの選択は Endel 再現度に影響しない。** Endel はネイティブなので、
  Flutter も React も Web も等距離。本当に同じスタックを再現するなら
  Swift + Kotlin + C++ を3本書くことになり、目的に見合わない
- Endel がネイティブを選んだ理由（watchOS/tvOS/visionOS/車載への展開、専任の
  オーディオエンジニアリングチーム）は、本プロジェクトには当てはまらない
- **再現度を決めるのはオーディオエンジンの設計であり、UIフレームワークではない。**
  ステム素材の質、オートメーション曲線、確率的スケジューリング、クロスフェードの作り込み
- Web Audio API は、ブラウザにおける Core Audio と同じ立ち位置の低レベルAPI。
  中間ライブラリを挟まなければ同等の制御粒度が得られる
- 参考: Endel の前身 BUBL（2013、子ども向けデジタルアートアプリ）の時点で、
  彼らは「操作に応じてリアルタイムに楽曲を生成する技術」を作り込んでいた。
  10年分の蓄積があるチームであることは念頭に置くべき
